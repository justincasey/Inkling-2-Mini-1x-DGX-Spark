# c=4 decode plan: what 200 tok/s aggregate needs, and where it can and cannot come from

Planning document (lane `k-c4plan`; no engine edit, no node run). Every number carries its source file or is marked DERIVED (a formula on sourced
numbers) or [INFERENCE] (not measured). The tables are printed by `python3 bench/tools/c4_model.py` (stdlib, offline, deterministic; `--validate`
prints the calibration and the residuals and exits 1 if a served point is off by more than 10 %); its arithmetic is pinned by
`python3 tests/test_c4_model.py`. Inputs by file are listed in the script's docstring; the router statistics were read once from node-1
(read-only header-range copy of the `router_*` planes, `bench/tools/c4_data/copy_planes_remote.py`, regenerated by `gen_fixture_stats.py`).

**Verdict in four lines.** (1) 200 tok/s is **not reachable byte-exactly** on the bench's four-kind mix: today's acceptance and bytes cap the
*snapshot* in which all four streams run at **196 tok/s at 100 % of the read bandwidth with no overhead at all** (section 4), and the A lane's
ladder of levers (A1-A5, every one delivered) lifts the sustained rate from about 130 to about 152 tok/s (bound with every overhead at zero:
183). (2) The span number the owner knows (`decode_c4_tok_s`: 101.1 drafted on bench.py's prompts, 111.4 on specbench's) is **27-30 % below the
steady state because of its tail** (section 1): 200 on that metric would need a steady 270+, above the byte roofline. (3) Traffic with
acceptance like code (or tool calls) **already reaches 200 on the A lane by the model** (4 x code: 205 span, 220 steady; 4 x tool 249): the
target is a property of the traffic, not of the engine, until measured otherwise (experiment E2). (4) On the bench mix, 200 needs the
A lane delivered **plus** two bit-changing levers at aggressive settings (experts skipped below 0.3 x the top weight, which drops 12.7 % of
the routing mass, and a 3.5 bpw expert pack; model: 200 on the rolling metric), or a 3.0 bpw pack alone: B lane, the owner's decision.

### 1.2 The tail artifact

`together()` divides all tokens by the span from the barrier to the **last** reply. It counts the prefill of the four prompts and the time in
which fewer than four streams run.

* **Serial c=4 has no tail**: the four streams advance in lockstep and end together (walls 25.37-25.47 s on the old engine, 20.39-20.48 s now,
  `graph-baseline` / `prefill-exact` raw). The artifact is the prefill only: the four prompts' solo ttft sum to 0.716 s of the 20.40 s span
  (3.5 %), so the steady serial step is **38.52 ms = 103.8 tok/s** against 100.4 tok/s as measured (DERIVED: (20.40 - 0.716) / 511).
* **Drafted c=4 has a large tail.** `spec-final/raw/A-specbench.json`, drafted, median of three: stream speeds 53.5 (code), 44.4 (json), 36.6
  (reasoning), 27.8 tok/s (chat) over 512 tokens = the streams finish at **9.57, 11.54, 13.97 and 18.39 s**. All four run only for the first
  9.57 s (52 % of the span); chat runs alone for the last **4.4 s (24 % of the span, 10 % of the tokens)**. With synchronous rounds (one round per active stream
  per window), the rounds per 512 tokens (264 chat, 89 code, 115 json, 160 reasoning, from the counters) give the round times by active streams:
  **100.8 / 76.0 / 54.4 / 42.3 ms at 4 / 3 / 2 / 1 active** (prefill 0.6 s [INFERENCE]). The 15.35 tokens of a 4-active round are therefore
  **152 tok/s of steady state against the 111.4 the span reports: the tail costs 27 %.** The model's fluid simulation (the table below) gives
  108.0 against 154.8.
* The c=8 figure of bench.py (125.9 drafted, 103.7 serial) is the same artifact seen from the other side: the server has four slots, so eight
  requests are two waves with slots refilled as streams end; it is not an eight-stream batch.

### 1.3 Proposed definition

* Keep `decode_c4_tok_s` exactly as bench.py computes it (continuity with every record) and call it the **span** number.
* Add **`decode_c4_rolling_tok_s`**: four workers in a closed loop, each running the four kinds back to back in a worker-specific rotation twice
  (8 requests per worker, 32 in all, 512 greedy tokens each, shipping defaults `SPEC=dspark PREFIX_CACHE=on VISION=on`, cold prefix cache per request as
  today, contexts 79-251 + 512), one request replaced the instant its predecessor ends; metric = all completion tokens / (first start to last end).
  Every worker sees the same mix, so the ends are close and the tail is at most the order effects at the last requests (the model gives
  94-97 % of the span with all four active). It is a real sustained-throughput number; the model's value today is **128.5-129.8 tok/s drafted,
  99.8 serial** (section 4.2 below).
* The 200 target applies to the rolling number (or to the span number if the owner insists: that needs a steady state of 270+, above the byte roofline;
  see section 4). Report both on every record.
* **Ladder rung** (`autoresearch.sh`, beside `r_speed_decode_100`): `r_speed_c4() { r_record speed-c4 --need-engine --min-tests 1 --metric decode_c4_rolling_tok_s --min-metric decode_c4_rolling_tok_s=<T> --same-engine spec; }`:
  the record gate is `speed-c4`; `--same-engine spec` ties it to a passing `spec` exactness record (drafted == serial, every output byte identical to the
  pinned engine's) of the same engine commit (`scripts/check_record.py`). Staged thresholds (proposal): 130 (today's model value, floor), 150
  (the A lane delivered), 200 (owner's, needs the B lane for this mix). The rung is the 54th.

## 3. The model

### 3.1 Formulas

For a window of S streams with `r_s` consecutive rows each (kinds `k_s`):

    T = O + (B_dense + B_unembed + sum_s B_kv(ctx) + B_experts + B_partials) / (BW x eff) + 0.034 ms x rows
    B_experts  = (U / 8) x E1(kinds) x bias,   U = 128 x (1 - prod_s (1 - d(k_s, r_s) / 128))
    B_partials = rows x 8 picks x (27,648 + 9,216) x 2 B x 48 visits           [INFERENCE: moe_experts.cu partial sums, written and read once]

`d(k, r)` = distinct experts a visit in `r` consecutive tokens of a real reply of kind `k` (`routelog.txt`: 8.0 for one row, 28.0-33.0 for eight);
streams are independent texts, so their windows combine by the closed form `U` (measured cross-text overlap of prompt rows is 2.6x random, an upper
bound for served streams: to first order it would shrink U by up to 16 % at four single rows; the held-out drafted c=4 round, already 7 % *faster* than served with the independent form, rules a large overlap out, so the closed form is kept). `E1` = expert bytes of one row over 48 visits with the kind's real 5-bit pick share (1.596-1.651 GB; 1.615 GB uniform) and `bias`
the routelog's byte-weighted ratio over the distinct-count ratio (0.99-1.0). `B_kv` = per stream 40 sliding visits x 1,031 x 4,096 B + 8 global
visits x ctx x 2,064 B (`ROOFLINE`; ctx 450 DERIVED). The unembed is read once per window for any rows <= 16 (`kernels-dense/ops-mini.txt`: 1,466 us at 1 row, 1,487 at 8;
NT = 2 above 16 rows, one tile decode and two mma passes: no measurement at 17-32 rows). The proposal is an input, not a model output: `timing.txt` (ctx 1,024: 7.42 / 7.91 /
8.94 ms for 1 / 2 / 4 requests; 8.31 / 8.89 / 9.92 at 4K, the engine's 8.3 / 8.9 / 9.9); its byte floor is **5.6 ms**, not 1.45 ms (corrected in `docs/DECODE-MEAN4-PLAN.md`: the 0.34 GB of drafter weights include the 103 MB folded Markov table, which each of the seven steps re-reads, plus the unembed's 0.35 GB: 1.31 GB), so the proposal can fall by about 1 ms with the same drafter arithmetic, which is what A1 attacks, and a drafted round also carries the residual of 2.8 ms (c=1) to 7.1 ms (c=4), linear in streams
(`Model.host_ms`; it is **not** in the bare model that the residual table judges).

**Two free parameters** (`O`, `eff`) fitted by least squares on three served steady serial steps with real routes: c=1 18.73 ms
(bench.py decode, 1000 / 53.394), c=2 25.95 ms and c=4 38.52 ms (the span times with the solo-ttft prefill taken out). Fit: **O = 4.72 ms, eff = 0.997**
(233.2 GB/s). Everything else comes from a file.

### 5.4 Tree / multi-candidate and a bigger batch

Verification of any drafting structure stays exact, but the extra rows cost experts. At four streams x 8 rows the union is 83 of 128 experts a visit; one extra row per stream
costs +3.0 ms and, at q = P(second candidate right | first wrong) = 1.0, buys 0.99 tokens a round (+3.4 %); at q = 0.35 it loses 0.8 %. Per-stream windows are capped at 8 rows

(106.9 of 128 experts at 8 streams). The bootstrap profile has four slots; c=8 with eight slots passes 200 on the A lane by the model.

## 8. Verdict

* **Is 200 reachable on the A lane? No, for the bench's four-kind mix.** Arithmetic: today's acceptance and bytes cost 1.19 GB a token, which is **196 tok/s at the 233.8 GB/s
  ceiling with zero overhead** for the snapshot; the rolling metric is 130 today and 152 after all five A levers (183 with every overhead at zero and a 258 GB/s stream); the span metric
  loses another 27 % to its tail. How far: 152 of 200 (76 %), a gap of x1.31 after the A lane. **What closes the rest:** B-lane bytes (skip 0.3 + 3.5 bpw, or 3.0 bpw) or higher
  acceptance (a better drafter, 3-7 points of mix), or a different definition (E7: eight slots; E2: code-like traffic).
* **Where 200 is reachable now by the model: acceptance-rich traffic** (4 x code 205 span / 220 steady, 4 x tool-call 249) and eight slots (220 steady). All three are extrapolations of the calibrated model to points not measured (E2, E7).
* **What the owner must decide:** (a) which c=4 number the target means: span (bench.py today, tail included), rolling (proposed) or steady; (b) which mix: bench.py's, the chat-like specbench's, or a code / tool-heavy one; (c) whether to approve
  the B-lane study (B1 first: no engine change), with the quality threshold KL < 0.0088 at the chosen skip; (d) whether eight slots counts for the target.
* **What the lead must decide:** schedule E0, E1, E2, E4 (measurements, 1 hour of node time in all); tell RoundOverhead that the host pool is 3-7 ms of a round, not 7-11 (message sent); integrate `-fuse` and `-round` (A1/A2, x1.05-1.15 together).
* **Recommended sequence:** E0 / E4 / E2 (settle the baseline and the model's extreme point) -> E3 + the rung (a number to optimise against) -> E1 and the grid replacement (all-chat c=4 stops losing 9 %) in parallel with A1+A2
  integration (E6) and E5 (kernel at 16-32 rows) -> A3 glue at c=4 -> B1 in parallel from the first day if the owner approves; copy hybrid, tree and a second block last or never.

## Defects and contradictions found (not fixed here)

* `docs/DECISIONS.md` and `spec-speed/README.md` ("Unexplained") attribute 7 / 11 ms of a round to the host from a comparison with `timing.txt`, whose ids are synthetic: most of it is expert bytes (section 2).
* The engine's `round_cost` grid (`ilp/engine.rs` `WINDOW_MS`) is built from the same synthetic table: it prices 4 streams x 8 rows at 53.0 ms against 89 modelled (about 90 served) and drives the depth allotment.
* `DECISIONS.md` quotes the 8-row window as 29.4 ms ("1.54 x one row") and `timing.txt` has 29.36 / 29.54 for two runs; it is a lab number: a real 8-row window is about 38 ms.
* `bench.py` says the server runs "SLOTS lanes (profile bootstrap 4...)" and still reports `decode_c8_tok_s` as if it were an 8-stream figure; README tables that quote c=8 as a scaling point mislead.
* `ROOFLINE.md` proposes 89 tok/s for four streams (85 % of an f = 1.08 byte roofline that omits the dense and KV traffic of the Mini and was derived for uniform routing); the serial c=4 byte floor is 118.5 tok/s and the engine already runs at 100-104.
* `--spec auto` does not combine the two drafters: the copy drafter runs only when the block drafter returns nothing for a stream (`engine.rs:2020`).
* `BudgetPolicy::parse` accepts `legacy`, but the env-var error text lists only `fixed, curve, plan, margin or scored`.
